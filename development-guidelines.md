# Development Guidelines

This service was generated by [pure-service-generator](https://github.com/beckfordp/pure-service-generator)
and follows [purerest](https://github.com/beckfordp/purerest)'s own design philosophy: pure
functional programming, no side effects outside the effect type, tagless-final style throughout.
These are the standards to keep applying as you extend this service beyond what was generated.

## Pure Functional Programming

- **Domain errors are ADTs, never exceptions used for control flow.** An expected, nameable
  failure (not found, invalid input, a downstream dependency unavailable) is a value in the
  return type — `Either`, `EitherT`, or equivalent — all the way from where it's detected to the
  HTTP edge. See `OrderError.scala`:

  ```scala
  sealed trait OrderError
  case object OrderNotFound extends OrderError
  ```

  Exceptions are reserved for genuinely unrecoverable failures (bugs, environment/startup
  failures) — not for a case you could instead enumerate and handle. This doesn't require
  eliminating exceptions baked into a third-party API's own contract (http4s's `Client[F]`/
  `HttpRoutes[F]` are inherently `MonadError`-based) — only your own expected failure modes need
  to be caught at the point they're known and converted to a typed result.
- **No partial functions on the happy path.** No `Option.get`/`Either.right.get`, no `head` on a
  possibly-empty collection, no non-exhaustive pattern match relying on a runtime `MatchError`.
  Prefer pattern matching, `fold`, or explicit handling of every case — see how
  `OrderRoutes.scala` handles `store.get(id)`:

  ```scala
  store.get(id).flatMap {
    case Some(entity) => /* ... */ .as(Right(OrderResponse(entity)))
    case None         => /* ... */ .as(Left(OrderNotFound))
  }
  ```
- **No `null`, no mutable `var` in domain code.** `Option`/`Either`/immutable data structures
  throughout. If something genuinely needs to change over time, use `Ref`/`Deferred`
  (cats-effect) — never a bare mutable field.
- **Impure operations are captured in `F`, not executed as bare side effects.** Randomness,
  wall-clock time, mutable state, or a synchronous/side-effecting third-party call all belong
  inside the effect type (`F.delay`, or a dedicated capability like `Random[F]`/`Clock[F]`) at
  the point they happen.
- **HTTP endpoints map typed domain errors to status codes explicitly, at the edge.** See the
  tapir `errorOut` wiring in `OrderRoutes.scala` (`notFoundOutput`) — there's
  no implicit/central exception-to-status translator. Add new error cases to the ADT and give each
  one its own explicit mapping, rather than reaching for a catch-all.

## Tagless-Final / Typeclass Style

Code is written against `F[_]: Async` (or a narrower capability typeclass), not a concrete effect
type. Dependencies are wired in via explicit combinators/constructor parameters (see how
`Main.scala` assembles `OrderStore`/`OrderRoutes`/
`HealthRoutes`), not annotations, reflection, or macros. Keep extending the service the same way —
an algebra as a trait parameterized by `F[_]`, a concrete instance built from capability
typeclasses, wired together explicitly at the composition root.

## ADTs & Domain Modeling

Model each domain concept as the smallest sum/product type that makes illegal states
unrepresentable — a `sealed trait` with `case object`/`case class` members for a closed set of
alternatives (like `OrderError`), a `case class` for a fixed set of fields.
Favor exhaustive pattern matches (the compiler will flag a new case you forgot to handle) over a
default/wildcard branch that silently swallows future variants.

## Patterns to Follow

- Typed error ADT → `errorOut` mapping at the tapir boundary, not thrown exceptions.
- `Option`/`Either` + pattern matching (`fold`, `case Some(...)`/`case None`) instead of
  unwrapping with `.get`.
- Dependencies passed as explicit constructor/method parameters (see `OrderRoutes.serverEndpoint`'s
  `store`/`logger` parameters).
- `purerest` (tracing, structured logging, metrics, resilience, tapir-based docs) consumed as a
  **published dependency** from GitHub Packages — never vendored or depended on via source.
- One dedicated Postgres database per service, named after the domain (singular) — this service
  never reads or writes another service's database directly.
- Plain resource JSON responses with standard HTTP status codes; errors as a small JSON error
  object whose status matches the mapped domain error — no response envelope spec (e.g. no
  JSON:API).

## Patterns to Avoid

- Throwing/catching exceptions for an expected, nameable failure case.
- `Option.get`, `Either.right.get`/`.left.get`, `.head` on a collection that might be empty, or
  any pattern match that isn't exhaustive.
- `null`, or a mutable `var` holding domain state.
- Calling a side-effecting or blocking API directly instead of capturing it in `F`.
- A central/implicit exception-to-HTTP-status translator in place of explicit, per-error-case
  `errorOut` mapping.
- Annotation-, reflection-, or macro-driven dependency wiring in place of explicit constructor
  parameters.
- Depending on `purerest` by source (`.dependsOn`) instead of the published GitHub Packages
  artifact.
- A second service reading or writing this service's database directly, or this service reading
  another service's database directly.

## Code Style & Testing

- Formatted with **scalafmt**, default Scala 3 style — run `sbt scalafmtCheck test` before
  committing (CI runs the same check and fails the build otherwise).
- Tests use **munit** + **munit-cats-effect**: an in-memory store for unit tests, a real,
  ephemeral Postgres container via **Testcontainers** for integration tests — no local Postgres or
  manual setup needed to run `sbt test`.
